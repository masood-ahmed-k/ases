The musl-versus-glibc trade-off of moving to Alpine is stated directly in the Dockerfile.

## What it found

- **py311-1's git was too old.** The first image (`python:3.11-slim`, Debian, git 2.47.3) could not open a repository WORKERGIT's own design had marked with `worktree.useRelativePaths=true`: git 2.48 sets `extensions.relativeWorktrees` on such a repository, and 2.47 refuses to open it at all. Found by running WORKERGIT's own live check against the real image, not by inspection.
- **Dubious ownership.** Alpine's git, run against a Windows bind mount owned by a different uid inside the container, refused to operate at all until `safe.directory /workspace` was set explicitly for the sandbox user: "detected dubious ownership in repository at '/workspace'".
- **The live check's own `rmtree` bug.** Stale root-owned directories from an earlier real-Docker run survived `rmtree(ignore_errors=True)` on Windows, because the files git had written inside the container came back read-only on the host side. A silent partial cleanup had been producing a false "insufficient permission" failure on the next run instead of actually cleaning up.
- **`GPG_KEY` in the base image's own environment.** The official Python image's Alpine variant sets `GPG_KEY`, a public signing-key fingerprint used to verify the Python source tarball, not a secret. The credential-shaped-name check does not know that on its own and needs an explicit exclusion by name.
- **The packed-refs.lock line.** A plain `git commit` inside the sandbox printed `error: Unable to create '/.git/packed-refs.lock': Read-only file system` and still exited 0. Tracing it with `GIT_TRACE_REFS` (round 16, commit e7e2ce8) showed the commit's own ref transaction had already succeeded; the error comes from git's sequencer cleanup afterward, deleting the absent `CHERRY_PICK_HEAD`/`REVERT_HEAD` pseudorefs, which needs `packed-refs.lock` in the read-only base `.git` mount. No git setting skips that cleanup, and making `packed-refs` writable would need the base mount writable, which is what keeps hooks and config out of a worker's reach, so this is accepted as a harmless, expected line, not fixed at the mount. Recorded as item 4 of `src/ases/sandbox.py`'s WORKERGIT notes.

## Hermes's own Docker terminal (HERMESDOCKER)

The checks above drive `sandbox.py`'s functions or `docker run` directly. `scripts/hermes_docker_terminal_check.py` (commit in merge 5bd81bf) drives Hermes 0.21.3's own code instead: `hermes_cli.config.apply_terminal_config_to_env` and `tools.terminal_tool.ensure_task_env`, which builds Hermes's own `DockerEnvironment`, with a copy of the real `coder-1` profile's `config.yaml` (never its `.env`) in a throwaway Hermes home, `TERMINAL_CWD` set to a throwaway worktree in the dispatcher's `<repo>/.worktrees/<task_id>` layout, and every command run through Hermes's own `execute`. Zero quota: no model is called and nothing under the Hermes home is written (the check compares `coder-1`'s `config.yaml` mtime and directory listing before and after). Run it with Hermes's own Python: `C:/Users/masoo/AppData/Local/hermes/hermes-agent/venv/Scripts/python.exe scripts/hermes_docker_terminal_check.py`.

**Its first runs found a blocker the standalone checks could not see.** Hermes runs every Docker terminal command as `bash -c ...` (`hermes-agent/tools/environments/remote_common.py`, `bash_argv`, hard-coded, no config key), and `ases-sandbox:py311-2` (Alpine) had only busybox `sh`, so every worker command failed with `exec: "bash": executable file not found in $PATH` (exit 127). The first real S1 dispatch in Docker would have failed on its first command, after spending quota. ASES's own sandboxed gate runs use `sh` and were never affected. Fix: `ases-sandbox:py311-3` adds `bash=5.3.9-r1` (pinned like git), every pin moved to it, `swarm init --apply` changed `coder-1`'s `terminal.docker_image` (backup `profiles/coder-1/config.yaml.ases-bak-20260928T135148Z`), and doctor is `HEALTHY` again. The same runs showed that four negative probes (hooks, config, network, env) had passed only because the exec never started; they now require their own exit marker, proving the command ran and failed for the expected reason.
