## Finding 0: run_gate silently converts a checkout infrastructure failure into a normal red gate

- Lens: gitexec-sandbox. Claimed severity: high. Verified severity: high. Location: `src/ases/gates.py` line 251.
- Scenario: git worktree add (host mode) or git clone/checkout (sandbox mode) fails for a reason that has nothing to do with the commit or the gate commands (disk full, a stale leftover directory, an AV lock, a git worktree-limit collision). run_gate returns GateResult(passed=False, detail='could not create gate <kind>: ...') with no exception raised, indistinguishable from a real failing test. mergeq.py:323-334 treats it as a failed Gate 3 candidate (spends fix-card budget on nothing). controller.py:1105-1160's post-merge Gate 3 re-check treats it as a failed re-check and calls mergeq.revert_merge(repo, outcome.squash_commit, ...) at line 1133, reverting an already-landed, correct merge purely because the throwaway re-check checkout could not be created.
- Evidence: Reproduced with repro_checkout_infra_fail.py (pre-occupying the path git needs for the worktree, unrelated to the commit/commands): gates.run_gate(repo, sha, 'gate1', ['echo hi']) returned GateResult(passed=False, detail="could not create gate worktree: Preparing worktree (detached HEAD e8fb53c)\nfatal: 'C:/Users/masoo/AppData/Local/Temp/ases-gate-fixed-x6zow9nz/wt' already exists") with no exception raised.
- Suggested fix (finder): Raise a distinct exception (reuse sandbox.SandboxInfrastructureError or add a matching gates-level one) when checkout(...).returncode != 0, instead of folding it into passed=False, so callers already written to treat an infra failure as 'not a red gate' (mergeq.py, review.py, controller.py's post-merge revert path) actually catch it instead of acting on it as a real failure.
- Skeptic's verdict: Read the actual source (not the claim's paraphrase) and reproduced the mechanism with the real git binary. All three code locations cited in the claim check out exactly as described.

1. src/ases/gates.py:251-253 (run_gate): `add = checkout(repo_path, commit_sha, worktree)` followed by `if add.returncode != 0: passed, output = False, f"could not create gate {kind}: ..."`. This is a plain return value, not a raised exception, for both host mode (`git worktree add`) and sandbox mode (`git clone`/`checkout`). The docstring even says explicitly "A runner that raises is not caught ... the caller decides what an infrastructure failure means (it is not a red gate)"  -  but that guarantee applies only to the `runner` callable, never to this checkout step, which silently becomes an ordinary `passed=False` GateResult.

2. src/ases/mergeq.py:317-334 (merge_task's Gate 3 candidate call): `gate_result = gates_mod.run_gate(...)`; `if not gate_result.passed: return MergeOutcome(False, candidate_sha, None, "fail", gate_result.detail)`. Nothing here distinguishes a checkout-infra failure from a real red gate 3. mergeq.py's own docstring only promises `sandbox.SandboxInfrastructureError ... propagates to the caller`  -  a checkout failure never raises that, so it never gets that treatment; it becomes a normal "fail" MergeOutcome.

3. src/ases/controller.py:1105-1160: the post-merge Gate 3 re-check wraps `gates_mod.run_gate(...)` in `except sandbox_mod.SandboxInfrastructureError as exc:` (line 1114) with an explicit comment that an infra failure here "is NOT a red gate ... must not trigger a revert." But `SandboxInfrastructureError` (defined in sandbox.py:113, docstring: "Raised by the runner sandbox_command_runner hands to gates.run_gate") is raised only from the command-runner path, never from run_gate's own checkout step. So a checkout-infra failure during this re-check is NOT caught by that except clause, falls through to `if postcheck is not None and not postcheck.passed:` (line ~1129), and calls `mergeq.revert_merge(repo, outcome.squash_commit, conn=conn, task_key=key, project=plan.project)` at line 1133 exactly as claimed  -  reverting an already-landed, correct merge because the throwaway re-check checkout could not be created.

I independently reproduced the core mechanism against the real git binary (no fakes): pre-occupying the target path `run_gate`'s worktree checkout uses (simulating a stale leftover directory / AV lock / any unrelated collision) makes `git worktree add` fail with a plain nonzero exit. `gates.run_gate` returned `GateResult(passed=False, detail="could not create gate worktree: ... fatal: '...\\wt' already exists")` with no exception raised  -  confirmed with a live script under C:/Users/masoo/ases-wt/_pytest/audit-verify-gitexec-sandbox-0/repro_checkout_infra_fail.py, PYTHONPATH pointed at the audit checkout's src/, using the project's own .venv Python. This is indistinguishable in shape from a real failing gate command, exactly as the claim states.

I also traced the fix-card-budget claim: mergeq.py's "fail" MergeOutcome reaches controller.py's `_handle_merge_failure` (~line 1191-1197), which opens a real Hermes fix card and increments `plan_tasks.fix_cards`, confirming "spends fix-card budget on nothing" is accurate, not speculative.

This is a genuine, reproducible high-severity defect: the codebase already has a deliberate, well-documented design principle ("a gate call that cannot even start is not a red gate," stated near-verbatim in controller.py:744-745 and sandbox.py:113-119) and implements it faithfully for the sandbox-runner failure mode, but the parallel checkout-infrastructure failure mode (worktree add / clone, which the same docstrings treat as part of "cannot even start") was never given the same exception-based signal, so it silently falls through every one of these purpose-built guards and both (a) burns real fix-card budget on phantom failures and (b) reverts a correct, already-merged commit purely because of a throwaway re-check checkout hiccup unrelated to the commit's actual content.

## Finding 1: sandbox.py never scrubs the environment of the docker-launching subprocess

- Lens: gitexec-sandbox. Claimed severity: medium. Verified severity: low. Location: `src/ases/sandbox.py` line 1073.
- Scenario: sandbox_command_runner's run() (line 1156), docker_available (1085) and image_present (1101) all call runner via _safe_run, which invokes runner(list(argv), timeout) with no env kwarg. default_runner's env defaults to None, which subprocess.run interprets as 'inherit the parent's full environment'. Unlike gates._run_commands (env = procenv.scrubbed_environ()) and every _git helper (gitexec.git_env()), the docker CLI process that performs every one of the controller's own sandboxed gate runs inherits the controller's full environment, including any credential-shaped variable and any DOCKER_HOST/DOCKER_CONTEXT/DOCKER_TLS_VERIFY override that happens to be set, which would silently redirect every 'isolated' gate run to a different daemon/context than the one sandbox.py's mount and flag checks were built for.
- Evidence: Reproduced with repro_env_not_scrubbed.py: with HERMES_PROVIDER_API_KEY set in the controller process, sandbox._safe_run(sandbox.default_runner, [sys.executable, '-c', "print(os.environ['HERMES_PROVIDER_API_KEY'])"], 10) (the exact call shape sandbox_command_runner uses) printed the secret value back, confirming the subprocess inherits the full parent environment.
- Suggested fix (finder): Have sandbox_command_runner build its process_runner default (and the docker_available/image_present calls it makes) with an explicit, scrubbed env (procenv.scrubbed_environ()), matching gates._run_commands's own pattern; leave default_runner's env=None default alone since key_visibility_test/exfiltration_probe rely on it staying unscrubbed by design.
- Skeptic's verdict: Confirmed the mechanical claim, but the "secret leak" framing is largely refuted and the severity is overstated.

What's TRUE (verified by reading the code, independently reproducing, and cross-checking docs/architecture.md):
- sandbox.py:1073 (_safe_run) calls `runner(list(argv), timeout)` with no `env=` kwarg.
- docker_available (sandbox.py:1085), image_present (sandbox.py:1101) and sandbox_command_runner's run() closure (sandbox.py:1156) all route through _safe_run, and the ONE production call site of sandbox_command_runner (gates.py:108, gates.resolve_runner) never passes a process_runner override, so all three use default_runner with env=None, which subprocess.run treats as "inherit the whole parent environment."
- I reproduced this independently in C:/Users/masoo/ases-wt/_pytest/audit-verify-gitexec-sandbox-1/repro_env_inherit.py: with HERMES_PROVIDER_API_KEY and DOCKER_HOST set in the parent process, a fake process_runner captured env=None on all three calls (docker info, docker image inspect, docker run), and a direct _safe_run(default_runner, ...) call to a child python -c printed both values back. This exactly matches the auditor's own reported repro.

What REFUTES the "secret leak" characterization:
- docker_run_argv (sandbox.py:916-999) builds the actual `docker run` argv itself and only adds `-e NAME=value` for entries explicitly passed in its own `env=` parameter (line 989: `for name, value in (env or {}).items()`). sandbox_command_runner's run() never passes env= to docker_run_argv (sandbox.py:1151-1153), so the container that executes the (potentially model-authored) gate command receives ZERO forwarded environment variables regardless of what the host-side docker CLI process inherited. The credential never reaches untrusted code; it only sits in the trusted docker CLI subprocess, which is not itself running model-authored code and is at the same trust level as the ASES controller that spawned it.
- docs/architecture.md:1131-1133 explicitly documents that sandbox.default_runner is deliberately left globally unscrubbed on purpose, "that runner also drives the Docker sandbox's own key-leak probes, which need to see a real, unscrubbed environment to actually detect a regression, so scrubbing it globally would have blinded the very probes meant to catch this class of bug." The architects were aware of this general tradeoff and built dedicated scrubbed wrappers (hermes.scrubbed_environ, profiles.py's _hermes_runner, gates._run_commands's procenv.scrubbed_environ()) everywhere the operator's credentials could reach untrusted code -- they just never built an equivalent wrapper specifically for sandbox_command_runner's docker-launching calls, which is a real, previously-unaddressed gap in that documented pattern, not evidence nobody thought about environment hygiene here.

What remains a genuine, narrower issue: the DOCKER_HOST/DOCKER_CONTEXT/DOCKER_TLS_VERIFY point. If any of those are set in the operator's environment for unrelated reasons, docker_available/image_present/the actual `docker run` would silently target a different daemon/context than sandbox.py's mount, cpu/memory/pids and mask checks assume. This is real and not covered by the container's own env isolation. But I found no evidence in the repo, blueprint.txt, or architecture.md that this project's actual operating environment ever sets those variables, so it is a latent risk rather than a demonstrated one.

The suggested_fix in the claim (wrap with procenv.scrubbed_environ()) would NOT fix the DOCKER_HOST/DOCKER_CONTEXT/DOCKER_TLS_VERIFY part at all: procenv.py's _CREDENTIAL_ENV regex is `(key|token|secret|passw|credential|auth|cookie|session)`, which does not match any of those three names, so they would survive the proposed scrub unchanged -- the fix as written only addresses the (already low-impact) credential-shaped-variable exposure, not the actual daemon-redirection risk the claim's own scenario text emphasizes most.
- Skeptic's reproduction: C:/Users/masoo/ases-wt/_pytest/audit-verify-gitexec-sandbox-1/repro_env_inherit.py, run with C:/Users/masoo/ases/.venv/Scripts/python.exe and PYTHONPATH pointing at the audit checkout's src. Output:
"direct _safe_run(default_runner, ...) stdout: 'sk-super-secret-value-12345|tcp://unexpected-remote-daemon.example:2375'" -- confirms both a credential-shaped var and DOCKER_HOST pass through.
"argv[:3]= ['docker', 'info', ...] env kwarg passed to process_runner: None" (and same for 'docker image inspect' and 'docker run --rm') -- confirms all three production call sites (docker_available, image_present, sandbox_command_runner's run()) call process_runner with no env kwarg, via gates.resolve_runner's sole call site (gates.py:108) which never overrides process_runner.
- Skeptic's corrected fix: Do not touch sandbox.default_runner (that would blind key_visibility_test/exfiltration_probe, per architecture.md:1131-1133 -- the auditor got this part right). Instead, give sandbox_command_runner its own explicit environment for the docker-launching calls only, following the same pattern profiles.py already uses for hermes (_hermes_runner wrapper) rather than changing the shared default. That environment needs to do two things procenv.scrubbed_environ() alone does not: (1) strip credential-shaped variables (procenv.scrubbed_environ() already does this), and (2) explicitly drop or pin DOCKER_HOST, DOCKER_CONTEXT, DOCKER_TLS_VERIFY and DOCKER_CERT_PATH so the docker CLI always targets the same local daemon sandbox.py's resource/mount checks were built for, since none of those names match procenv's credential regex and would otherwise pass through unchanged. Concretely: build a small wrapper (e.g. in sandbox.py, next to default_runner) that calls default_runner with env=dict(procenv.scrubbed_environ(), **{k: v for k, v in [] }) after popping the four DOCKER_* keys, and have sandbox_command_runner's process_runner default to that wrapper instead of default_runner, while leaving default_runner itself and its existing callers (key_visibility_test, exfiltration_probe) untouched.

## Finding 2: adopt_current_head at swarm run startup permanently launders an untrusted HEAD into the base-check allow-list

- Lens: basecheck. Claimed severity: high. Verified severity: high. Location: `src/ases/cli.py` line 1065.
- Scenario: swarm run is restarted (after a crash, Ctrl-C, or a wrapper/cron re-invocation -- explicitly a supported flow: cmd_run's own docstring says 'Ctrl-C ends it... re-run swarm run to continue'). Between the previous swarm run exiting and this one starting, the primary checkout's HEAD is moved to a commit ASES itself never wrote (a stray git operation on the primary checkout, exactly the ASES-GIT-12 threat guards.py's own module docstring names: 'a stray write into the primary checkout is possible'). At the next startup, cli.py:1065 calls `guards_mod.check_primary_checkout(repo, plan.integration_branch)` with NO `expected_head` argument, even though `guards_mod.expected_head(conn, plan.project)` (the SHA this same project adopted last run) is available and IS used for this exact comparison later, every pass, at controller.py:2268. Skipping it here means check_primary_checkout only verifies branch name and a clean tree, never that HEAD is still where ASES left it. check_primary_checkout therefore reports ok=True with zero problems. cli.py:1071 then unconditionally calls `guards_mod.adopt_current_head(conn, plan.project, repo)`, which re-baselines integrity_state AND appends the rogue SHA to integrity_heads (schema v9) forever, via set_expected_head's own ON CONFLICT DO NOTHING upsert -- there is no way to later remove it. From that point on, guards.written_heads(conn, project) contains the rogue commit permanently, so guards.check_card_base treats ANY work card whose branch was created from that rogue commit as a verified, legitimate base -- indefinitely, not just for the one pass where the drift happened. This defeats the round 10 base-commit check's entire purpose (ASES-GIT-01/ASES-GIT-16) for exactly the class of tampering ASES-GIT-12 exists to catch, and does so silently: no event, no warning, nothing in guard.problems.
- Evidence: Reproduced empirically against the real guards.py module (not a fake): adopt_current_head(conn, project, repo) on a clean repo records head1. A rogue commit is then made on the integration branch (simulating drift between two swarm run invocations, exactly as cli.py's own bootstrap/reconcile code path never checks for). Calling `guards.check_primary_checkout(repo, "master")` exactly as cli.py:1065 does (no expected_head) returns `ok=True, problems=()`. The following `guards.adopt_current_head(conn, project, repo)` (cli.py:1071) then adopts the rogue head, and `guards.written_heads(conn, project)` afterward contains the rogue SHA alongside the original one -- confirmed with `rogue head now permanently in the base-check allow-list: True`. Cross-checked against tests/unit/test_cli_run.py and tests/unit/test_cli_commands.py: every test of this startup path monkeypatches both `check_primary_checkout` and `adopt_current_head` with argument-swallowing lambdas (`lambda *a, **kw: ...`), so no existing test could ever notice that the real call site omits expected_head -- exactly the kind of gap the task brief predicted a fake would hide.
- Suggested fix (finder): Pass the project's previously recorded expected head into the startup check, e.g. `guards_mod.check_primary_checkout(repo, plan.integration_branch, guards_mod.expected_head(conn, plan.project))` at cli.py:1065, and refuse to start (or require an explicit override) when that comparison fails, the same way a mid-run divergence is already refused. A first-ever run (expected_head is None) is unaffected, since check_primary_checkout already treats None as 'skip the comparison'.
- Skeptic's verdict: Verified against the real (non-mocked) source at every point the claim cites.

1. src/ases/cli.py:1065-1071 (_run_loop, called unconditionally by every `swarm run` invocation, first-time or restart): `guard = guards_mod.check_primary_checkout(repo, plan.integration_branch)` passes no third argument, then `guards_mod.adopt_current_head(conn, plan.project, repo)` runs unconditionally regardless of guard outcome details beyond ok/not-ok.

2. src/ases/guards.py:130-184 `check_primary_checkout`'s `expected_head` parameter defaults to `None`, and line 169 shows `None` means "skip the HEAD-moved comparison entirely" (`elif expected_head is not None and head != expected_head`). ## Finding 3: process_card_base_checks can false-positive-block a legitimate card dispatched by Hermes's own live gateway dispatcher, because it can run before the worktree/branch it is checking exists

- Lens: basecheck. Claimed severity: medium. Verified severity: medium. Location: `src/ases/controller.py` line 2125.
- Scenario: The architecture doc documents that Hermes's own gateway dispatcher is routinely a separate, already-running process polling the same board concurrently with ASES's own controller pass ('The dispatcher is already live (a multiplexed gateway the user runs for other purposes also polls this board)', docs/architecture.md line 76-77; the same doc records this exact class of race already firing for the review-lane check). Hermes's claim_task (kanban_db.py:2210, via _claim_and_open_run) commits `UPDATE tasks SET status='running' ...` in its own database transaction and returns BEFORE `_resolve_worktree_workspace`/`_ensure_git_worktree` (kanban_db_dispatch.py:1880-1893, kanban_db_workspace.py:422-438) has run the `git worktree add [-b] <branch> <path> <start>` subprocess that actually creates the branch and its reflog. If ASES's controller pass calls `hermes_mod.kanban_list(board, status='running')` in that window -- after the status commit, before the worktree/branch materializes -- `guards_mod.check_card_base(repo, branch, allowed)` is invoked for a branch that does not exist in the repository at all yet. check_card_base treats 'cannot find the base' identically to 'wrong base' (guards.py:680-681, by design, fail-closed), so `process_card_base_checks` immediately calls `questions_mod.ask_user(...)`, which for a `running` card calls `hermes_mod.kanban_block(..., kind='needs_input')` (questions.py:400-403) and pulls the card OUT of `running` into `blocked` -- yanking a brand-new, perfectly legitimately-based worker out from under itself over a transient timing artifact, with no retry: once blocked, this function no longer sees the card in its `running` listing, so it is never re-checked and stays blocked until a human answers the ASES-GIT-01/ASES-GIT-16 question. The docstring of process_card_base_checks does not mention or guard against this window at all; the round 10 architecture note itself admits 'the check has not yet run against a real dispatch.'

## Finding 10: Gate command timeout does not bound wall-clock execution on real Windows; a hung gate command wedges the merge queue indefinitely

- Lens: windows-real. Claimed severity: high. Verified severity: high. Location: `src/ases/gates.py` line 128.

## Refuted

- data: Quality/plan reports can silently show the wrong merge_records row (stale legacy data instead of the real one) when a task_key has both a legacy and a project row. Why refuted: Confirmed true: merge_records' PK is (project, task_key) since schema v8 (db.py lines 281-352), and mergeq._upsert_merge_record's real-project branch (lines 344-382) does INSERT ... ON CONFLICT(project, task_key) DO UPDATE, which never finds or updates an existing (NULL, task_key) legacy row. So a task_key can genuinely carry both a legacy NULL-project row and a real project's row, and both match report.py:554-559's and finalgates.py:872-878's WHERE task_key IN (...) AND (project IS NULL OR project = ?), with no ORDER BY before the dict comprehension.

Refuted: the specific failure the claim describes (dict silently keeping the stale/wrong row) does not happen with the actual code and the project's actual SQLite engine. I reproduced the two-row precondition through the real write path (ases.mergeq._upsert_merge_record) and ran the exact query from report.py/finalgates.py across 8 variations: small table, forward and reverse insertion order, a 500-row and a 20000-row padded/skewed table, with ANALYZE run, and with 5 simultaneously colliding task_keys mixed into a 40-key IN(...) list (matching production's multi-key shape). EXPLAIN QUERY PLAN showed SQLite consistently choosing a MULTI-INDEX OR plan for this "(col IS NULL OR col = ?) AND col2 IN (...)" shape against the (project, task_key) index: it emits all rows matching "project IS NULL" first, then all rows matching "project = ?" last, in the literal order the WHERE clause disjuncts are written, regardless of each row's rowid/insertion order or the table's size/statistics. Because a Python dict comprehension keeps the last-assigned value for a repeated key, the row matching the current project always wins in every trial; the stale NULL row never won, even when I deliberately inserted it after the project row to test recency-based failure too.

This means the absence of ORDER BY is real but currently harmless for this exact query text and this SQLite build (3.45.1, the project's own venv) -- the outcome is deterministic, not "whichever happens to be last" as the claim states, and it deterministically favors the correct row. This is implementation-defined behavior rather than an SQL guarantee, so it is fragile (a different SQLite version, or someone flipping the OR operands to "project = ? OR project IS NULL", could change the outcome), but that is a robustness/defensive-coding concern, not a currently reproducible wrong-data defect as claimed.
