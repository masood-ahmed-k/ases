## Finding A2-0: swarm run's ASES-MOD-02 pre-flight runs AFTER the wall clock has already started, reintroducing finding 8's own bug

- Lens: run-start. Claimed: high. Verified: medium. Location: `src/ases/cli.py` line 1158.
- Scenario: An operator (or the plan's own approve-to-run drift, which _first_model_rejection's own docstring says is exactly why it is rechecked at run time) pins an under-provisioned or unknown-context model for a role in config/models.yaml between `swarm approve` and `swarm run`. ## Finding A2-1: process_card_base_checks + guards.branch_exists can leave a card's base commit unchecked forever, with zero visibility, and cannot tell a never-created branch from a deleted one

- Lens: run-start. Claimed: medium. Verified: low. Location: `src/ases/controller.py` line 2141.
- Scenario: Round 12's fix for finding 3 adds `if not guards_mod.branch_exists(repo, branch): continue` before the base-commit check, to avoid false-positive-blocking a card whose branch Hermes has not yet materialized. But the skip has no bound and records nothing (the docstring says so itself: 'skipped this pass, unrecorded'). (a) If a card's branch is NEVER created (Hermes's worktree-add subprocess fails permanently -- disk, permissions, a name collision, a Hermes-side bug -- and Hermes never marks the card failed), the card stays `running` in Hermes's kanban forever, and this check silently no-ops on it every single pass, forever, with no event and no warning anywhere in ASES. (b) guards.branch_exists() cannot distinguish 'never created' from 'created, then the ref was deleted' (by a stray/adversarial deletion of exactly the ASES-GIT-12 kind guards.py's own module docstring warns about, or by hardening.py's cleanup racing a stale Hermes 'running' status): both cases resolve to the identical `code != 0` result, so a branch that existed and then vanished is treated exactly like 'not yet created' and is also silently skipped forever, instead of being escalated -- defeating the ASES-GIT-01/GIT-16 detection this function exists to provide, in exactly the scenario (a branch's provenance becoming unverifiable) it is meant to catch.
- Evidence: Live repro against the real functions (script: C:/Users/masoo/ases-wt/_pytest/audit2-runstart/repro_stuck_card.py): a fake `running` card whose branch is never created is run through controller.process_card_base_checks for 5 simulated passes. Output for every pass: 'reasons=[] events_recorded=0 branch_exists=False' -- confirming the card is never checked, never recorded, never escalated. Separately (script: C:/Users/masoo/ases-wt/_pytest/audit2-runstart/repro_deleted_branch.py, against the real guards.branch_exists): 'never created: False' / after `git branch <name>`: 'created: True' / after `git branch -D <name>`: 'deleted: False' -- identical to the never-created case, confirming branch_exists (and therefore its only caller) cannot tell the two apart.
- Suggested fix (finder): Track a per-(card_id, branch) 'first seen missing' counter or timestamp, the same grace-key pattern guards.check_idle_worktrees already uses for the analogous re-dispatch race, and only keep silently skipping for a bounded number of passes or a bounded time. Once that bound is exceeded, escalate exactly like a real check_card_base failure (ask_user + card_base_violation) instead of skipping forever -- this is the exact refinement finding 3's own skeptic corrected fix called for ('after a bounded number of consecutive misses so a genuinely missing/expired reflog is still eventually reported'), which the landed round 12 fix does not implement.
- Skeptic's verdict: The two pure-code facts underlying the claim are verified true by direct reading and repro:
(1) controller.py:2141-2143 (`if not guards_mod.branch_exists(repo, branch): continue`) is an unconditional, unbounded skip: no counter, no timestamp, nothing recorded (repro_stuck_card.py reproduces "reasons=[] events_recorded=0" across 5 passes with a fake permanently-running card whose branch never exists).
(2) guards.branch_exists (guards.py:636-637) is `rev-parse --verify -q` and truly cannot distinguish "never created" from "created then deleted" (repro_deleted_branch.py confirms both return False identically).
(3) r12_audit_findings.md's own Finding 3 skeptic explicitly asked for "a bounded number of consecutive misses so a genuinely missing/expired reflog is still eventually reported," and the round-12 diff (6c1a369..f7d4672, controller.py ~2141) does not implement any such bound - confirmed against the actual diff.

However, the claim's two motivating real-world scenarios do not hold up:
Scenario (a) is factually wrong about Hermes's actual behavior. I read Hermes's real source (C:\Users\masoo\AppData\Local\hermes\hermes-agent\hermes_cli, read-only, same precedent Finding 3's own skeptic used). kanban_db_dispatch.py's `_dispatch_lane_task` wraps `_resolve_worktree_workspace`/`_ensure_git_worktree` in a try/except; `_ensure_git_worktree` (kanban_db_workspace.py:422-434) raises RuntimeError on any non-zero `git worktree add` exit (disk, permission, or name-collision failures all produce this). The except clause calls `_record_task_failure(..., release_claim=True, end_run=True)`, which resets the card's status away from `running` (back to `ready`/`review` for retry) and, after `DEFAULT_FAILURE_LIMIT = 2` (kanban_db_dispatch.py:34) consecutive failures, trips it to `blocked`. So for every concrete cause the claim names (disk, permissions, name collision), Hermes does NOT leave the card `running` forever with no failure marked - it retries at most twice then blocks it, which is a card ASES's own kanban_list(status="running") will stop reporting. Only a truly exotic case (the Hermes process itself crashing between the claim-commit and the try block, e.g. OOM-kill/power loss) would produce the described state, which is not what "a Hermes-side bug" in the claim demonstrates or reproduces.

Scenario (b)'s proposed "hardening.py's cleanup racing a stale Hermes running status" mechanism also does not hold up: hardening.py's `_read_board`/`_consider_branch` (hardening.py:290-303, 613-625) re-reads the CURRENT board status inside the same cleanup pass and explicitly protects any branch whose card is not in `_FINISHED` (`if name in self._active_branches: return self._skip(...)`), so a genuinely-running card's branch is never a hardening deletion candidate through any path I could find in this codebase. The "stray/adversarial deletion" alternative is real in principle but is external tampering, not a normal operational path, and guards.py's module docstring (lines 1-22) is about primary-checkout writes and worktree-content changes, not specifically branch-ref deletion, so citing it as a direct warning about this exact failure mode overstates the connection.

Net: the code-level gap is real and the round-12 fix genuinely omits the bound its own prior audit asked for, but the practical trigger is narrower than claimed (out-of-band/adversarial branch deletion, not an ordinary Hermes worktree-add failure), and even when triggered it only defers detection (mergeq's own `_check_base` still backstops any actual merge, exactly as Finding 3's own severity reasoning already established) rather than causing incorrect behavior. That downgrades it from the claimed medium to low.
- Skeptic's reproduction: Ran the two provided scripts unchanged: `PYTHONPATH=C:/Users/masoo/ases-wt/audit2/src C:/Users/masoo/ases/.venv/Scripts/python.exe C:/Users/masoo/ases-wt/_pytest/audit2-runstart/repro_stuck_card.py` -> confirms "reasons=[] events_recorded=0 branch_exists=False" for all 5 simulated passes. `.../repro_deleted_branch.py` -> confirms branch_exists returns False identically for "never created" and "created then git branch -D'd". Additionally read Hermes's real source (kanban_db_dispatch.py:1219-1300 `_record_task_failure`, 1874-1893 `_dispatch_lane_task`; kanban_db_workspace.py:422-434 `_ensure_git_worktree`) to confirm a real worktree-add failure IS caught and does transition the card out of `running` within at most 2 attempts (DEFAULT_FAILURE_LIMIT=2), and read hardening.py:290-303, 613-625 to confirm its cleanup explicitly protects any card not in a finished state, refuting the proposed race mechanism.
- Skeptic's corrected fix: Keep the suggested bounded-miss counter (mirroring guards.check_idle_worktrees' grace-key pattern), since it is real and still unimplemented, but correct the motivating scenario before filing: drop the "Hermes never marks the card failed" framing (Hermes's own _record_task_failure/DEFAULT_FAILURE_LIMIT=2 already handles a real worktree-add failure and moves the card out of `running`), and reframe the risk as "an out-of-band deletion of a card's branch ref while Hermes still reports it running is treated identically to the benign not-yet-created race and skipped forever with zero visibility," which is the part actually demonstrated by the reproductions. Severity: low, not medium, given the narrower trigger and the existing mergeq._check_base backstop against any bad merge actually landing.

## Finding A2-2: The finding-8 reordering widens the window in which a concurrently-running swarm run's own pause can be silently overridden back to 'running' without going through swarm resume

- Lens: run-start. Claimed: low. Verified: low. Location: `src/ases/cli.py` line 944.
- Scenario: _refuse_unless_startable reads project_state once, before the (now potentially slow, git- and DB-touching) reconcile pass runs; _start_project_or_refuse's call to bounds.start_project only happens after reconcile completes -- a much wider window than existed pre-round-12, when the paused-check and the start_project call were back-to-back. bounds.start_project's own write is a genuine backstop for 'stopped'/'finished' landing in that window (both are excluded from its UPDATE's WHERE clause and its pre-check, so it correctly raises StateError, honoring the docstring's 'a stop that lands between our read and our write still wins'). But that same WHERE clause explicitly lists 'paused' as a startable status (`WHERE status IN ('planning', 'running', 'paused')`), so if the project becomes paused during the widened window, start_project silently flips it back to running -- exactly what _refuse_unless_startable's own explicit paused-check exists to prevent ('a pause is a decision for the operator, who lifts it with swarm resume'). In this codebase 'paused' is set only from inside a swarm run process's own pass loop (controller.py's pause_and_report, on a reached bound), never by a separate command, so reaching this requires two swarm run invocations racing on the same project -- a configuration nothing in cli.py's startup sequence (_load_project/_open_conn/_load_plan) guards against, though also not one the codebase documents as supported.
- Evidence: Direct repro against the real bounds.start_project (script: C:/Users/masoo/ases-wt/_pytest/audit2-runstart/repro_pause_resume_gap.py): start_project() called on a project already at status='paused' returns successfully with status flipped to 'running' and no exception raised, while the identical call on a status='stopped' project correctly raises StateError. No lock file, mutex, or other single-instance guard was found anywhere in cli.py's `_run_loop`/`_open_conn` path.
- Suggested fix (finder): Have _start_project_or_refuse re-read project_state immediately before calling bounds.start_project and refuse if it is now 'paused' (mirroring _refuse_unless_startable's own check), rather than relying solely on bounds.start_project's write-time guard, which by design does not cover 'paused'.
- Skeptic's verdict: All load-bearing parts of the claim check out against the real code and against a live repro I ran independently (not just re-running the claim's own script).
